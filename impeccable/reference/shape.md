# Shape

Produce a UX/UI brief that can guide implementation. An explicit `$impeccable shape` request is planning only: do not write product code. For craft, shaping contributes the single substantial-work spec; reuse an existing approved brief.

## Discovery

Read the request, relevant code, and available PRODUCT.md/DESIGN.md. Infer routine details from that evidence. Ask about missing inputs only when they materially change scope, behavior, audience, or design direction. Honor an explicitly requested interview, but do not repeat answered questions or force an answer round when the brief is already clear.

Useful topics, selected for the task:

- Purpose, audience, context, and the primary user action.
- Real content/data, typical and extreme volumes, and required imagery.
- Scope: screen versus flow, sketch/prototype versus production, interactivity, and constraints.
- Key states and feedback, navigation, accessibility, responsive/native requirements.
- Existing identity, references, palette/type direction, and any explicit anti-goals.

Keep questions focused; use a permitted structured input tool when available or concise conversation otherwise. For optional aesthetic choices, propose a concrete direction with its reason instead of turning preferences into a long menu.

## Optional visual exploration

Use sketches, wireframes, or image comps when the user asks to compare directions or when they resolve a substantial visual ambiguity. Choose the medium that answers that question; image-generation availability does not make probes mandatory. Existing approved references may already answer it.

If generating comps or assets, consult [codex.md](codex.md). Integrate the result into this brief and its approval; do not create separate palette/mock confirmation loops. Keep controls, content, behavior, and accessibility explicit because an image cannot specify them fully.

## Brief

Default to a compact brief. Expand only the parts the task needs:

1. Purpose, target audience, and core flow.
2. Scope and fidelity, including what the implementation will deliver.
3. Visual direction: existing identity or a justified composition/type/color direction; any selected reference.
4. Layout and interactions, including the key states and realistic content ranges.
5. Content and asset requirements, likely sources, and any material missing input.
6. Relevant implementation references and the checks needed to verify the result.

Distinguish facts, assumptions, recommendations, and unresolved decisions. Do not persist task-specific scope into product context documents unless requested.

Deliver the brief as the requested planning result. For substantial implementation that has not yet been approved, ask for approval of this concrete brief and stop before code. If approval already exists, identify how the brief reflects it and return to the authorized implementation workflow. A planning-only request is complete when the brief and material open questions are delivered; it does not require an extra confirmation to be considered finished.
